# 複数のセッションを同時に動かすとき

このツールキットは7つのJOBに分かれている。**案件が増えれば、CLI AI のセッションも
同時に複数動く。** そのとき何が起きるか、どう避けるかを書く。

以下は **Claude Code の場合**である。Codex には該当する機能が無いため、
その場合は「同じ落とし穴があること」だけを読み、対処は利用者が担う。

---

## 1. 実際に起きたこと

1日のあいだに3つのセッション（月次レポート／単発レポート／基盤整備）が
同じリポジトリを触り、次の4件が起きた。

| 起きたこと | 原因 |
| --- | --- |
| 共通部品を直したまま、コミットせず放置された | 他のセッションが触っているか誰も知らなかった |
| 「リポジトリに取得スクリプトは無い」と誤って結論した | 自分の担当JOBの下だけを見た。`shared/` を見なかった |
| `git switch main` で自分の変更が消え、スクリプトが動かなくなった | 自分の変更が未マージだと分かっていなかった |
| 2つのセッションが同じファイルを触るPRを別々に出した | 分岐する前に相談していなかった |

**4件すべて、隣のセッションに一言聞けば済んだ。**

### 根本の原因は「作業ツリーが1つしかない」こと

案件ごとにフォルダは分かれていても、**共通部品のリポジトリは1つ**である。
`ANDA_REPO` のような環境変数で1か所を指していれば、全案件がそこを見る。

つまり **1つのセッションがブランチを切り替えると、他の案件がその影響を受ける。**
自分の作業が終わったら `main` に戻す、という約束が要る。

ただし**マージされる前に `main` へ戻すと、自分の変更が消えて動かなくなる。**
マージされるまではブランチのまま、マージ後に戻す。

同時に共通部品を編集する場面が増えるなら、`git worktree` で案件ごとに
作業ツリーを分けるのが本来の解である。

## 2. セッション同士は直接話せる

Claude Code は、同じ利用者の他のセッションを一覧でき、メッセージを送れる。

```
ListAgents            いま動いているセッションの一覧（名前・状態・開始時刻）
SendMessage           名前を宛先にして送る
```

一覧には状態が出る。`idle` なら手空き、`shell` ならコマンドの実行中。

**セッション名は、その作業フォルダに由来する名前が付くことが多い。**
どのセッションがどの案件かは名前から推測できるが、**断定はできない。**
聞くときは「心当たりがなければ、そう答えてください」と添える。

### 手空きになったら知らせてもらう

相手が作業中のとき、返事を催促してはいけない。
一度だけ通知を受け取る仕組みがあるので、それを使う。

```
SendMessage に notify_when_idle を付ける
（メッセージを付けなければ、相手に何も届かない純粋な購読になる）
```

**「終わりましたか」を繰り返し送らない。** 一覧を繰り返し見に行くのもしない。

---

## 3. 何を聞き、何を聞かないか

ここが要点である。**話せるからといって、何でも渡してよいわけではない。**

| 直接聞いてよい | 利用者を経由する |
| --- | --- |
| 事実の確認（「このPRは君が出した?」） | 方針の決定（「この方式でいくか」） |
| 状態の共有（「共通部品を触っている?」） | クライアントへの約束・納品の可否 |
| 技術的な質問（「この壁をどう回避した?」） | 費用・期限に関わる判断 |
| 済ませた検証の共有 | 相手の作業の優先順位を変えること |

**指示ではなく確認として送る。** 「こうしてください」ではなく
「こう理解しているが合っているか」と書く。判断は利用者のものである。

送るときは、こう書き添えると相手の手を止めない。

> 作業中でしたら、切れ目で構いません。そちらを止めないでください。

### 済ませた検証は、必ず添える

相手に同じ作業をやり直させてはいけない。実例：

> こちらで済ませた検証（同じことをやり直す必要はありません）
> ・現在の main との競合：なし（試行マージで確認）
> ・テスト3種：すべて終了コード0
> ・後方互換：保たれている

これが無いと、相手は同じ確認を最初からやる。**時間は利用者の時間である。**

### ★ 断られた操作を、隣に代行させない

**権限はセッションごとに設定されている。** 自分が許可を得られなかった操作を
他のセッションに頼むのは、利用者の判断を回り込むことになる。

できない操作は、**隣に振らず利用者に戻す。**

## 4. 他のセッションのPRをレビューするとき

自分が出していないPRが並んでいることがある。マージの判断は利用者がするが、
**検証は先に済ませておくと早い。**

```bash
git fetch origin
git merge-base origin/<相手のブランチ> main      # どこから分岐したか
git checkout -b review origin/<相手のブランチ>
git merge --no-commit --no-ff main               # 競合するか（試すだけ）
git merge --abort
```

見るところは4つ。

1. **分岐点が古くないか。** 相手が分岐したあとに main が進んでいれば、
   相手はそれを知らない可能性がある
2. **同じファイルを触っていないか。** 競合しなくても、意図が衝突していることがある
3. **後方互換が保たれているか。** 既存の呼び出しがそのまま通るか実際に動かす
4. **テストが通るか。** 相手のブランチに main を合わせた状態で走らせる

**確かめ終わったら、作業ツリーを `main` に戻す。** 他の案件が待っている。

自分が作ったものに相手が手を入れている場合は、**意図が合っているかを本人に聞く。**
勝手に解釈して進めると、設計の意図が二重になる。

## 5. やってしまった失敗

**この文書を書いた本人が、この機能の存在を確認せずに作業していた。**

利用者に「この文面を隣のセッションに貼ってください」と何度もお願いした。
`ListAgents` を一度も呼んでいなかった。**利用者を伝書鳩にしていた。**

同じ日に、私は別のセッションへ次のルールを書かせている。

> 「無い」と言う前に、その場で見て確かめる。以前見たときの記憶で結論を出さない。

**自分が守っていなかった。**

教訓は単純である。**手段が無いと決める前に、一覧を見る。**
`ListAgents` は1回の呼び出しで済み、相手に負荷もかけない。

---

## 6. 最低限の約束

- 着手時に `ListAgents` を1回呼び、誰が動いているか見る
- 共通部品を触る前に、他のセッションが触っていないか聞く
- ブランチを切ったら、**マージ後に** `main` へ戻す
- 催促を送らない。手空きの通知を使う
- 指示ではなく確認として送る。判断は利用者のもの
- **断られた操作を隣に代行させない**
