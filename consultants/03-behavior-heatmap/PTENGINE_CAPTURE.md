# Ptengineヒートマップを位置ずれなくキャプチャする

JOB 03の補助手順。Clarity版（[CLARITY_CAPTURE.md](CLARITY_CAPTURE.md)）と同じ狙いで、
**熱の位置と画面要素の位置が一致した画像**を機械的に撮る。

Clarityを使う案件はそのまま。**ツールが違うだけで、所見の書き方は同じ**である。

## 1. Clarityと何が同じで、何が違うか

| | Clarity | Ptengine |
|---|---|---|
| 下敷き | **保存済みのスクリーンショット**（凍結されている） | **実サイト**を毎回読み込む |
| 状態の指定 | URLのクエリ（`?date=…&Device=…&heatmapType=…`） | **URLに載らない。**UIの状態でクライアント側に保存される |
| スクロール | `#heatmapVisual` の `scrollTop` | `div.deviceScrollWrap` の `scrollTop`（同じ性質） |
| 種別 | タップ / スクロール | クリック / 滞在 / 離脱 / コンバージョン |
| 実数 | 画面の集計値をJSで抽出 | GraphQL（`getHeatMapData` ほか） |

**同じなのはスクロールの仕組み**で、ここがキャプチャの中核である。
違うのは状態の持ち方と、下敷きが生きていること。この2つが新しい危険を生む。

## 2. 画面の構造（実機で確認）

```text
document（対象サイトのページ）
  └ iframe#pt-heatmap              … UI全体。同一オリジンなので中を読める
      ├ div.deviceScrollWrap       … スクロールコンテナ
      │   ├ iframe                 … 対象ページ（実サイト）
      │   └ canvas.hm-canvas       … 熱レイヤー。ページ全高ぶん描画済み
      └ ツールバー（種別・デバイス・期間）
```

`scrollTop` を書き換えたときの実測値。

```text
scrollTop = 3000 にすると
  ページ側の scrollY    0 → 3000   （ちょうど追従）
  熱レイヤーの位置   +180 → −2820  （ちょうど −3000）
```

**ずれ幅が `scrollTop` と厳密に一致する。** したがって結合位置は計算で決まり、
画像差分で重なりを探す必要がない。Clarityと同じ方法がそのまま使える。

## 3. 手順

### 初回のみ：サインイン

```bash
python -m pip install -r requirements.txt
python -m playwright install chromium
python scripts/ptengine_heatmap_capture.py --login
```

ブラウザが開くのでPtengineにサインインし、**窓を閉じたら完了**（キー入力は不要）。
認証情報は `.ptengine_profile` に保存される。**このフォルダはGitに追加しない**（`.gitignore` 登録済み）。

### 1ページ分をまとめて撮る

```bash
python scripts/ptengine_capture_set.py \
    --sid <ワークスペースID> \
    --page-url https://example.com/lp/a.html \
    --name lp_a --date 2026-08
```

ワークスペースIDは、Ptengineのアプリを開いたときのURL `…/app/<ここ>/insight/…` にある。

出力は `<out>/lp_a_pc_click.png` のような決まった名前になり、
`lp_a_capture_log.json` に**撮影条件と、撮れなかった組み合わせ**が残る。

### 1枚だけ撮り直す

```bash
python scripts/ptengine_heatmap_capture.py \
    --sid <ワークスペースID> \
    --page-url https://example.com/lp/a.html \
    --type click --device Mobile --date 2026-08 \
    --out output/lp_a_sp_click
```

| オプション | 既定 | 用途 |
|---|---|---|
| `--type` | `click` | `click` / `attention`（滞在） / `exit`（離脱） / `conversion` |
| `--device` | `Mobile` | `Mobile` / `Desktop` / `Tablet`。PCとSPを混ぜない |
| `--date` | `last-month` | **月次では暦月を渡す**（`2026-08`）。範囲は `2026-08-01..2026-08-31`。遡れるのは約12か月（⑱） |
| `--window-height` | `1600` | **タイル枚数を左右する**（§4-①） |
| `--timeout` | `90` | 描画完了を待つ上限秒。PC表示は20秒以上かかる |
| `--settle` | `10` | 初回描画の待機秒 |
| `--trim` | `auto` | 左右の余白を落とす位置。`L,R` で明示、`none` で落とさない |

## 4. 実機で確かめて分かったこと

### ① 表示領域が狭い。ウィンドウの高さでタイル枚数が決まる

Ptengineの表示領域は、上のツールバーのぶんだけ低い。実測で
**「ウィンドウの高さ − 約220px」**だった。

```text
ウィンドウ 1200 → 表示 633px → 12,400pxのページが 55枚
ウィンドウ 1600 → 表示 約1,380px → 同じページが 約13枚
```

枚数が増えると、時間がかかるだけでなく**継ぎ目も増える**。
既定を1600にしてあるが、画面の大きいPCではさらに増やしてよい。

### ② 状態がURLに載らない。**残ったまま次の撮影に持ち越される**

ここが Clarity との最大の違いで、いちばん危険なところである。

デバイスをPCへ切り替えたあと、**URLを変えて開き直してもPCのままだった。**
状態はクライアント側に保存され、URLにもファイル名にも痕跡が残らない。

Clarity ⑨ の事故（フォルダ名は対象月なのに中身は「過去30日」）と同じ型だが、
**Clarityは少なくともURLに出ていた。Ptengineは出ない。**

そのためスクリプトは、撮る直前に画面から状態を読み戻し、
**指定と違えば撮らずに止める。**

```text
画面の状態が指定と違います。撮影を中止します。
  デバイス: スマートフォン のはずが ['PC', 'クリックヒートマップ']
```

読み戻した値は `capture_meta.json` の `observedSelection` / `observedDateLabel` に残す。
**指定ではなく、実際に画面に出ていた値を残す**のが要点である。

### ③ 下敷きが生ページ。**過去の熱が現在のページに乗る**

Clarityは保存済みのスクリーンショットに熱を重ねるが、Ptengineは実サイトを読み込む。

同じ条件で連続して撮っても、ページ全高が変わった。

```text
スマートフォン  12,400 → 12,406
PC              14,145 → 15,013
```

**サイト改修があった月は、熱の位置と画面要素が食い違う。**
先月のデータを今月の画面に重ねることになるが、画像を見ても気づけない。

対策として、撮影時点の全高を `pageHeightCss` に必ず残す。
まとめ撮りの最後に全高を表示するので、**前月の記録と見比べる**。
大きく違えば、ページ自体が変わっている。

### ④ 種別によって、描き方も右の表も違う

| 種別 | 描き方 | 右の表 |
|---|---|---|
| クリック | 熱＋クリック順位のバッジ | 要素名／クリック数／クリックシェア |
| 滞在（アテンション） | 面で塗る熱 | 同様 |
| 離脱 | **熱ではなくブロック単位の率ラベル** | ブロック名／インプレッション率／離脱率 |
| コンバージョン | **どのコンバージョンを見るかの選択が別に要る** | 設定がなければ何も出ない |

**コンバージョンは、そのページに設定がなければ何も描かれない。**
まとめ撮りは1種別が撮れなくても止まらず、`capture_log.json` の `skipped` に残して次へ進む。

### ⑤ 「読み込み中」の表示は当てにならない

熱レイヤーが描けているのに `[class*=loading]` が残っていることを実測で確認した。
これを完了判定に使うと、いつまでも待つか、途中で撮ることになる。

代わりに**熱レイヤーの高さ**を手がかりにする。描画途中は高さが足りないか、そもそも存在しない。

ただし**「スクロール領域の全高と一致すること」を条件にしてはいけない**（⑮）。
一致するとは限らず、待ち続けることになる。
**高さが動かなくなったこと**をもって描き終わったとみなす。

なお離脱とコンバージョンは熱のcanvasを使わず、**ブロック単位の％ラベル**で描く。
種別によって見る手がかりが違う（④）。

### ⑥ UIの操作は重い。切り替えた直後にJSを実行すると固まる

種別を切り替えた直後にページのJSを呼んだところ、45秒待っても返らなかった。
デバイスの切り替えは、PC表示で20秒以上かかる。

**切り替えのあとは、状態を短く何度も読んで待つ。** 一度に長い処理を投げない。

### ⑦ タブもカレンダーも、クラス名では選べない

種別タブは `h-8 min-w-10 flex px-3 …` のようなユーティリティクラスしか持たず、
どれがどの種別かを見分ける印がない。**表示名で選ぶ。**

カレンダーの日セルはさらに厄介で、`<td class="available">` だけを持ち、
**日付を表す属性がない。しかも前後の月の日が同じ表に並ぶ。**
（月送りの矢印は例外で、クラス名に向きが入っている。⑰を参照）

```text
2026年9月のカレンダー先頭行:  30  31  1  2  3  4  5
                             ↑8月末     ↑ここから9月
```

素直に「1」を探すと8月31日の隣の「1」を押しかねない。
そこで**「1から始まる一番長い連番」を当月とみなして**選び、
最後に期間ラベルを読み戻して確かめる。

### ⑧ ウィンドウを狭めない。狭いと種別が選べなくなる

種別タブのラベルは `hidden lg:block` で、**画面が狭いと文字が消えてアイコンだけになる。**
表示名で選んでいるため、狭い窓では「種別が選べません」で止まる。
`--window-width` は既定の1920から下げないこと。

### ⑨ 未来の日は選べない

カレンダーの未来日は `class="normal disabled"` で、押しても効かない。
**対象月が終わる前に撮ろうとすると、ここに当たる。**
黙って効かないと分かりにくいので、理由を返して止めるようにしてある。

```text
2026年9月30日は選べません（未来の日付）。対象月が終わってから撮ってください
```

### ⑩ 期間ピッカーは、閉じていてもDOMに残る

`.pt-picker-panel__shortarea` は閉じていても存在する。
**要素の有無で「開いている」と判定すると、常に開いていることになる。**
中の項目が**見えているか**（`offsetHeight`）で判定する。

ボタンはトグルなので、すでに開いているときに押すと閉じる。開くまで押す。

### ⑪ トークンは必要。URLを組み立てて直接開くことはできない

ヒートマップを開くURLには `ptengine_heatmap_token` が付く。
**これは必須で、リストの行をクリックしたときに発行される。**

> **最初、これを「要らない」と誤って結論した。** すでにヒートマップを開いた
> ことのあるタブで試したため、トークンが保存済みで、消しても動いたのである。
> **まっさらなプロファイルで試したら、UIそのものが出なかった**（`hasUI: False`）。
>
> 一度でも通った環境で確かめると、必要なものを「要らない」と判断してしまう。
> 認証やトークンの要否は、**新しいプロファイルで確かめる。**

そのため、対象ページは毎回**リストから開く**。

```text
…/app/<sid>/insight/pagescene/pagescenelist   ← ここから行をクリックする
```

なお**対象ページ自身のクエリ（utm など）は消さない。**
クエリで内容が変わるページがあり、落とすと違うページを撮ることになる。

### ⑫ リストは1ページに10件しか出ない。検索窓で絞り込む

リストの初期表示は10件で、**それ以外のページは行が存在しない。**
「行が見つかりません」で止まるが、原因はURLの間違いではなく、単に載っていないこと。

検索窓（`placeholder="キーワードをご入力ください"`）にパスを入れて絞り込む。
スクリプトはこれを自動で行う。

```text
[*] リストを「/guide/117」で絞り込みました
```

### ⑬ リストは入れ子の別オリジンiframeの中にある

リストは `reportv3.ptengine.jp` の iframe に描かれる。
**メインのドキュメントを探しても行は見つからない。**
ヒートマップ本体（`iframe#pt-heatmap`）とは別の枠なので、混同しない。

### ⑭ 貼り付く要素は、画像の統計ではなく**DOMから測る**

Clarityは下敷きが保存済みのスクリーンショットなので、画像の統計から測るしかない。
**Ptengineは下敷きが生ページで、同一オリジンで中を読める。** ならば直接測れる。

画像の統計に任せて実際に外した。**熱はページと一緒に動き、貼り付くヘッダーの上を
流れていく。** そのためヘッダーの帯はタイルごとに絵が変わり、Clarityで効いていた
「ばらつきが小さい」という手がかりが働かない。

```text
実測 HEADER（fixed・画面幅）  72px
画像の統計による判定    8px   ← 継ぎ目ごとにヘッダーが並んだ
```

対象にするのは**画面幅に広がり、上端か下端に接している帯**だけ。
隅の丸いボタン（実測：50×50、下端から95px上）は切らない。
そこまで切ると本文を145px失う。丸いボタンが邪魔なときは `--hide` で消す。

どちらで決めたかは `capture_meta.json` の `stickySource`（`dom` / `image`）に残る。
`dom` なのに継ぎ目が出るなら、`--sticky-top` で明示する。

### ⑮ 熱レイヤーの高さは、ページ全高と一致しない。**一致を待ってはいけない**

⑤ で「熱レイヤーの高さがスクロール領域の全高とほぼ一致すること」を完了の条件にしたが、
**これは誤りだった。**

熱レイヤーの高さは「**Ptengineが計測したときの**ページ高さ」である。
下敷きが生ページである以上、いま読み込んだページの高さとは一致しない。
しかも**実行ごとに変わる。**

```text
同じページ・同じ期間・同じデバイス（PC）
  1回目  ページ 11642 / 熱 11642   … 一致（まとめ撮りはこれで通った）
  2回目  ページ 11642 / 熱 14198   … +2556px
  3回目  ページ 11642 / 熱 12344   … +702px（60秒見ても動かない）
```

一致を待つと、**描画は終わっているのに時間切れになり、
「データが無い可能性があります」という見当違いの理由が出る。**

そこで「高さが3回続けて動かないこと」を完了の条件にした。
一致したときは即座に完了とする（それ以上待つ理由がない）。

食い違いの意味は、**高い側と低い側で違う。** 並べて確かめた。

| | 意味 | 扱い |
|---|---|---|
| 熱 > ページ | 上端ぞろえで、余りが下に伸びるだけ。**上・中・下のどこでも位置は合っていた** | 記録に残すだけ |
| 熱 < ページ | **下の方に熱が存在しない** | 警告する。下端を目で確かめる |

> 最初、+2556px を見て「下へ行くほど位置がずれる」と書いた。**測ったら外れていた。**
> 一致した回と食い違った回の同じ位置を並べたところ、
> 上・中・下のすべてで内容も熱も同じ位置だった。
> **差が出たら、まず並べて確かめる。**

両方の高さは `capture_meta.json` の `pageHeightCss` / `heatHeightCss` に残る。

### ⑯ 月次で「先月」を使ってはいけない。**プリセットに読み替えてもいけない**

Clarity ⑨ と同じ。プリセット（今月・先月・過去7日間）は**実行した日から決まる。**
`--date 2026-08` のように暦月を渡す。

**暦月を渡されたら、プリセットに読み替えない。** 以前は「先月」と一致すれば
プリセットで済ませていた。月送りが解決するまでの回避策だったが、これは
**実行した日に依存する**。月末の23時台に始めた取得が日付をまたぐと、
「先月」の指す月がその場で1つずれる。いまは暦月を必ずカレンダーで指定する。

**年のずれは、月の見出しで防いでいる。** 日セルを押すのは
「2026年8月」のように**年を含む見出しと一致した表の中だけ**である。
適用後の期間ラベルには年が無い（「08/01-08/31」）ため、
選ぶ時点で年をそろえておかないと、あとの照合では年のずれを見つけられない。

### ⑰ 月送りは、**本物のマウス操作では動かない**

矢印はクラス名で選べる。⑦で「クラス名では選べない」のは種別タブと日セルの話で、
月送りは別である。**中身がSVGで文字が入っていない**ため、
矢印の文字（‹ ›）を探すやり方では見つからない。

```text
pt-picker-panel__icon-btn pt-icon-d-arrow-left    « 年を戻す
pt-picker-panel__icon-btn pt-icon-arrow-left      ‹ 月を戻す
pt-picker-panel__icon-btn pt-icon-arrow-right     › 月を進める
pt-picker-panel__icon-btn pt-icon-d-arrow-right   » 年を進める
```

**押し方が期間ボタンと逆である。** 同じ画面の中で作法が違う。

| | DOMの `click()` | 本物のマウス操作 |
|---|---|---|
| 期間ボタン（ピッカーを開く） | **効かない** | 効く |
| カレンダーの月送り | **効く** | **効かない** |

本物のマウス操作は例外も出さずに素通りする。ボタンは見つかり、
`disabled` でもなく、クリックは成功するのに**月が変わらない**。
どちらかに揃えようとすると、片方が黙って効かなくなる。

パネルは2か月ぶん並ぶので、どちらかに目的の月が出ていればよい。
1か月ずつでは古い月で何十回も押すことになるため、
12か月以上離れていれば年送りでまとめて詰める。

### ⑱ 遡れるのは約12か月。**それより古い月は「未来の日付」に見える**

古い月のセルは、未来の日と同じ `disabled` になる。
区別する情報がセル側に無いため、最初は理由を「未来の日付」と決め打ちしていた。
その結果、**1年以上前の月を指定すると「未来の日付です」と表示された。**

`disabled` かどうかだけをJS側から返し、**理由は日付と今日を比べて決める。**

実測した境目（2026-09-15 に確認）。

```text
2025-10-01  選べる
2025-09-01  選べない   ← 約365日の移動窓
```

この幅は契約内容で変わる可能性がある。撮れない月に当たったら、
まず画面のカレンダーを目で見て、その月が選べるかを確かめる。

### ⑲ 閉じかけのピッカーは、一瞬「開いている」ように見える

ピッカーのボタンはトグルなので「開いていなければ押す」と書く。
ところが、直前の「適用」で閉じ始めた枠はまだ高さを持っている。
そこを見にいくと開いていると判断して押さずに進み、そのあと枠が消えて、
次の操作が「要素が見えません」で落ちる。

**500ms あけて2回続けて開いていること**を条件にする。
それでも押せないときは、待つのではなく**開き直してから**試す。

## 5. まとめて撮る理由

Clarityは理由が2つあった。**Ptengineで残るのは、そのうち1つだけである。**

**貼り付く要素の高さは、Ptengineでは種別に関係なく測れる。**
Clarityでは画像の統計に頼るしかなく、面で塗られる種別（スクロール・滞在・離脱）では
手がかりが働かないため、クリックで測った値を引き継いでいた。
Ptengineは下敷きが生ページなので、**どの種別でもDOMから同じ値が読める**（⑭）。
それでもまとめ撮りはクリックの値を他へ渡している。
**同じページの8枚が同じ高さで切られていることを、記録の上で保証するため**である。

**左右の余白の判定が、種別ごとに食い違う。こちらはPtengineでも残る。**
点が疎に散るクリックは狭く出る。面で塗られる種別は広く出る。
別々に切ると、同じページ・同じデバイスなのに幅の違う画像ができ、並べると縮尺がずれる。
**全種別の判定を持ち寄り、広い側でまとめて切る。**

> **狭い側に合わせてはいけない。** Clarityで実際に、2枚とも入力欄が右端で
> 切れた画像ができた。寸法は一致していたので、数字だけでは気づけなかった。

この2つの処理は `scripts/heatmap_image.py` に置き、Clarityと共用している。
**片方で見つけた改善が、もう片方にも届く。**
`tests/test_heatmap_image.py` が、上の落とし穴を塞いだままであることを毎回確かめる。

## 6. 画像を所見にするときの注意

Clarityと同じ（[AGENTS.md](AGENTS.md)・[CLARITY_CAPTURE.md](CLARITY_CAPTURE.md) 6節）。

- 熱の位置と画面要素の対応を、**要素名または画面領域の言葉**で記述する
- 期間・デバイス・サンプル数を必ず併記する
- 「押されている」ことと「押したかった」ことは別。仮説として分けて書く
- **下敷きが撮影時点のページであることを明記する。** 対象期間とページの状態が
  食い違っている可能性は、Ptengine固有の但し書きとして残す
