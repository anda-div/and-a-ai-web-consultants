# Clarityヒートマップを位置ずれなくキャプチャする

JOB 03の補助手順。ヒートマップ画像を証拠として使うには、
**熱の位置と画面要素の位置が一致していること**が前提になる。
ここがずれた画像は所見の根拠にならない。

## 1. なぜずれるのか

Clarityのヒートマップ表示は、ページのスクリーンショットの上に熱のレイヤーを重ねて描いている。
表示領域の外にある部分は、スクロールして描画されるまで熱が確定しない。

そのため、次の方法ではずれや欠けが起きやすい。

| 方法 | 起きること |
|---|---|
| 画面の一括ダウンロード | 表示領域外の熱が反映されず、位置が合わない |
| ブラウザの全画面キャプチャ拡張 | 重ねレイヤーが追従せず、熱だけが固定される |
| マウスホイールでのスクロール＋画面キャプチャ | ホバーでツールチップが出て画面に写り込む。スクロール量が一定にならない |

## 2. 解決の考え方

ヒートマップ表示領域は `#heatmapVisual` という**独立したスクロールコンテナ**である。

- `scrollHeight` はキャプチャ対象ページの全高（CSS px）
- `clientHeight` は1画面分の高さ
- **`scrollTop` を書き換えると、ページ画像と熱のレイヤーが同期して動く**

つまり、マウスを一切使わずに `scrollTop` を段階的に進めれば、
どの位置でも熱と画面が一致した状態でキャプチャできる。
さらに `scrollTop` の実測値が分かるので、**結合位置を計算で決められる**
（画像差分で重なりを探す必要がない）。

```js
const c = document.getElementById('heatmapVisual');
c.scrollHeight;      // 例: 7626  … ページ全高
c.clientHeight;      // 例: 1128  … 1画面分
c.scrollTop = 900;   // 熱とページが一緒に動く
```

## 3. 手順

月次で使うのは `scripts/clarity_capture_set.py` の方。1ページ分（PC・SP ×
クリック・スクロールの4枚）を1コマンドで撮る。所要は1ページ約2分。

```bash
python scripts/clarity_capture_set.py \
    --project <projectId> \
    --page-url https://example.com/category/shoes/ \
    --name shoes
```

出力は `<out>/shoes_pc_click.png` のような決まった名前になり、
`shoes_capture_log.json` に撮影条件が残る。

以下は、その中で呼ばれている `scripts/clarity_heatmap_capture.py` の説明。
1枚だけ撮り直したいときは直接使う。

### 初回のみ：サインイン

```bash
python -m pip install -r requirements.txt
python -m playwright install chromium
python scripts/clarity_heatmap_capture.py --login
```

ブラウザが開くのでClarityにサインインし、ターミナルで Enter を押す。
認証情報は `--profile` のフォルダ（既定 `.clarity_profile`）に保存され、次回以降は再利用される。

**このフォルダは認証情報を含む。Gitに追加しないこと**（`.gitignore` に登録済み）。

### キャプチャ

```bash
# 絞り込み前・タップ
python scripts/clarity_heatmap_capture.py \
    --project <projectId> \
    --page-url https://example.com/category/shoes/ \
    --type tap --device Mobile \
    --out output/shoes_tap

# 絞り込み後・スクロール
python scripts/clarity_heatmap_capture.py \
    --project <projectId> \
    --page-url https://example.com/category/shoes/ \
    --url-match "https://example.com/category/shoes/?stock=in&facet%5B%5D=round" \
    --op exact \
    --type scroll --device Mobile \
    --out output/shoes_filtered_scroll
```

出力:

```
output/shoes_tap/
├── tiles/tile_000.png …        分割キャプチャ（原本を残す）
├── heatmap_tap_joined.png      結合画像
└── capture_meta.json           URL・期間・デバイス・ページ全高・各タイルのscrollTop
```

`capture_meta.json` があれば、その画像がどの条件で撮られたかを後から証明できる。
JOB.md Step 1 の画像台帳にはこのファイルの内容を転記する。

### 主なオプション

| オプション | 既定 | 用途 |
|---|---|---|
| `--type` | `tap` | `tap` / `scroll` |
| `--device` | `Mobile` | `Mobile` / `Desktop` / `Tablet`。PCとSPを混ぜない |
| `--date` | `Last 30 days` | UIの選択肢と同じ文字列 |
| `--op` | `exact` | URL照合。`exact` / `contains` / `endswith` / `exclude` |
| `--overlap` | `40` | タイル間の重なり（CSS px）。固定ヘッダーがある場合は増やす |
| `--tile-delay` | `1.2` | 1タイルごとの待機秒。熱の描画が追いつかない場合は増やす |
| `--settle` | `8.0` | 初回描画の待機秒。縦に長いページでは増やす |
| `--timeout` | `45` | 表示領域が現れるまで待つ上限秒 |
| `--trim` | `auto` | 左右の余白を落とす位置。`L,R` で明示、`none` で落とさない（⑧） |
| `--channel` | なし | `chrome` を指定するとインストール済みChromeを使う |

## 4. 通しで動かして分かったこと

実機で通した結果、**1ページ4枚（PC/SP × クリック/スクロール）が約2分**で揃った。
見守りは要らない。手作業の目安が1ページ10分だったので、大きく短くなる。

通す過程で7つ直した。同じ環境なら同じ順で出る。

### ① デバイス指定が名前と逆

`Device` はセッションの絞り込み、`heatmapDeviceType` は**どの画面幅で描画するか**。
両方そろえないと、スマートフォンで絞り込んでもPC幅の画面が出る。

実際に撮って幅と高さを見て確かめた対応は次のとおり。**名前から想像すると逆になる。**

| `heatmapDeviceType` | 画面幅 | ページ高さ | 実体 |
|---|---|---|---|
| `0`（既定値） | 410px | 12471px | スマートフォン |
| `1` | 1413px | 10236px | タブレット |
| `2` | 1492px | 6471px | PC |

既定が `0` なので、**指定を忘れるとPCのつもりでスマートフォンを撮る**。
撮れた画像が縦に細長いのに気づかないと、そのまま資料に載ってしまう。

### ② 画像の下半分が真っ白になる

高さに「ページ全高」を使うと起きる。Clarityは表示領域の幅に合わせてページを縮小する
ため、**実際にスクロールできる量はページ全高より小さい**（27734px と 12531px）。
実際にスクロールできた範囲で高さを決める。

### ③ 左右に広い白帯が残る

Clarityは表示領域の中央にページを縮小表示する。そのまま資料に貼ると、
ページが小さく余白ばかりの図になる（1498px 中 410px しか中身がない）。

「白でない画素が1つでもある列」を探す方法では切れない。枠線やスクロールバーが
端に写り込んでいるため。**列ごとに中身の割合を見て、割合の高い列が連続する
一番長い区間**を取る。

ただし、これを画像ごとに任せると**同じページ・同じデバイスなのに幅が違う画像**が
できてしまう（⑧）。

### ④ 継ぎ目ごとにヘッダーや固定バーが繰り返す

画面に貼り付く要素は、すべてのタイルに写り込む。2枚目以降は上を、
最後以外は下を切り落とす。そこに入るはずの中身は、隣のタイルの重なり部分が持つので、
**重なりを切る高さの合計より広く取っておく**。

高さは自動で測れる。ただし**上端と下端で効く手がかりが違う**。

| 端 | 使う手がかり | 理由 |
|---|---|---|
| 上（ヘッダー） | タイル間の**ばらつき** | 半透明で後ろが透けるため「1枚目と同じか」では判定できない。それでも本文よりばらつきが小さい（実測：ヘッダー38 / 本文83） |
| 下（固定バー・チャット） | 1枚目との**一致** | ばらつきが本文と近く分けられない（実測：下端15 / 本文19）。絵そのものはよく一致する |

### ⑤ スクロールマップでは自動判定が効かない

全面が色で覆われ、どの位置も同じように見えるため、上のどちらの手がかりも働かない。
そのままだと**スクロールマップだけ継ぎ目にヘッダーが並ぶ**。

**同じページのクリックマップで測った値を引き継ぐ。**
`clarity_capture_set.py` がこれを行う。1ページ分をまとめて撮るのは、
見た目の都合ではなくこの依存関係のためである。

なおスクロールマップではヘッダーが厚く描かれることがある。引き継いだ値でまだ帯が出る
場合は `--scroll-sticky-top` で増やす（実例ではクリック69pxに対し180pxで消えた）。

### ⑥ 1画面に収まるページは、スクロールしない

ログインだけのページなど、内容が少ないページでは**表示領域がスクロールしない**。
スクロールデータが 5%〜95% すべて「訪問者の100%」・ドロップオフ0%、
つまり全員が最下部に到達しているページである。

以前は「スクロールできること」を条件に待っていたため、こうしたページで
「表示領域が見つかりません」と誤って失敗していた。
スクロールしないなら、分割せず**1枚で撮ればよい**。

### ⑦ ヒートマップではないものを撮っていた（重要）

⑥ と組み合わさって、**別の要素を撮る**という事故が起きていた。

`#heatmapVisual` がスクロールしないと、代替探索が
**左側の「クリック数の多い順にランキング」パネル**を選んでしまう。
このパネルはスクロールする長い箱（実測：312要素・37,000px）なので、
「スクロールできる大きなdiv」の条件に合ってしまう。

```
誤  94 × 33,263 px … ランキングパネル
正 567 ×    962 px … ヒートマップ
```

**寸法が異常だったから気づけた。** 縦横比がそれらしい値だったら、
ヒートマップでないものがレポートに載っていた可能性がある。

**`#heatmapVisual` があるなら、それ以外は見ない。**
代替探索は「idが変わったとき」だけに限る。

撮れた画像は、必ず**寸法を確認する**。
幅が極端に狭い、または縦横比が他のページと大きく違う場合は疑う。

**そして、画像そのものを開いて見る。** 寸法が妥当でも中身が切れていることがある
（⑧ で実際に起きた）。少なくとも1ページは目で見る。

### ⑧ クリックとスクロールで、画像の幅がそろわない

③ の余白落としを画像ごとに判定させると、こうなる。

```
H09_MyPage_PC_Click.png    567 × 962
H10_MyPage_PC_Scroll.png  1492 × 962   ← 同じページ・同じデバイス
```

理由は、**判定の材料が種別ごとに違う**こと。

| 種別 | 画像の中身 | 余白と判定される列 |
|---|---|---|
| クリックマップ | 点が疎に散る | 多い（中身の割合が10%を超えない列が出る） |
| スクロールマップ | 熱の帯が全幅に及ぶ | ほぼない |

幅が違うと、2枚を並べたり同じ枠に収めたりしたときに縮尺がずれる。
所見が「この位置」と指している場所も合わなくなる。

**どちらかに合わせるのではなく、両方の判定を持ち寄って広い側で揃える。**
「どちらかが中身と見なした列は切り落とさない」という決め方である。

実装は「2枚とも**切らずに**撮り、そろってから一括で切る」形にした。
`clarity_capture_set.py` が両方に `--trim none` を渡し、それぞれの判定を
`capture_meta.json` の `trimDetected` から読んで、広い側で2枚とも切る。

```
--trim auto     自分で判定（既定。1枚だけ撮るときはこれ）
--trim 5,1483   左右を明示
--trim none     余白を落とさない（まとめ役が後で切る）
```

実際に使った左右は `trimLeftRight`、その画像自身の判定は `trimDetected` として
`*_capture_log.json` に残る。あとから同じ幅で撮り直せる。

#### 狭い側に合わせてはいけない

**クリックマップの判定は狭く出る。** 点が疎なため「中身がない列」と
見なされる列が多い。実測では**常に**クリック側が狭かった。

| ページ | クリックの判定 | スクロールの判定 | 差 |
|---|---|---|---|
| ログインのみのページ（PC） | 605px | **1478px** | 873px |
| 同（SP） | 366px | **398px** | 32px |
| 内容の多いページ（PC・SP） | 一致 | 一致 | 0 |

縦に長く中身の詰まったページでは一致する。**短くて余白の多いページで食い違う。**
列ごとの「中身がある割合が10%以上」という判定が、行数の少ないページでは
厳しすぎるためである。

はじめクリック側に合わせる実装にしたところ、**2枚とも入力欄が右端で
切れた画像**になった。寸法は一致していたので、数字だけでは気づけなかった。

> **寸法の確認だけでは足りない。** 幅がそろっていても、中身が切れていることがある。
> ⑦ の教訓（撮れた画像は寸法を確認する）に加えて、**画像そのものを開いて見る。**
> 特に、判定値が他のページと大きく違うページは必ず見る。

### ⑨ 実行中に共通スクリプトを書き換えない

`clarity_capture_set.py` は、1枚ごとに `clarity_heatmap_capture.py` を
**別プロセスとして起こす**。そのため、取得中にこのファイルを編集すると、
**途中の1枚から書き換え後のコードが読まれる**。

実際に、PC の2枚を撮り終えた時点で編集が入り、SP の2枚が
`AttributeError: 'tuple' object has no attribute 'name'` で落ちた。
関数の戻り値を増やす途中の状態を読んでいた。

取得は数分かかる。**終わるまで待つ。** 待てないなら、
編集用にリポジトリを別の場所へ複製してからにする。

### 補足1：縦に長いページは待ち時間を延ばす

描画に時間がかかり、既定の待ちでは「表示領域が見つかりません」で止まる。
`--settle`（初回描画の待ち）と `--timeout`（表示領域を待つ上限）を渡せる。
実例では、3万px級のページで既定の8秒では足りなかった。

### 補足2：「表示領域が見つかりません」の切り分け

このエラーには原因が複数ある。**うち1つは、こちらでは直せない。**

| 原因 | 見分け方 | 対処 |
|---|---|---|
| サインインが切れた | **さっきまで撮れていたページも撮れなくなる** | 再サインインが必要（お客様側の操作） |
| 描画が終わっていない | 縦に長いページだけで起きる | `--settle` と `--timeout` を延ばす |
| URL照合が0件 | そのページだけ、最初から一度も撮れない | `--op` を変える（`exact` / `contains` / `endswith`） |

**まず「さっきまで撮れていたページ」を1本だけ動かす。** それも落ちるなら
サインイン切れで、ページ側の問題ではない。原因を1回の実行で切り分けられる。

同じページに何度も試すのは、切り分けとしては役に立たない。

サインイン切れかどうかは、画面の文字で確かめられる。

```
お帰りなさい! / セッションの有効期限が切れました。もう一度サインインしてください
```

Clarityのセッションは短い。**月次の取得を始める前に、1本試しておく**のが早い。

### 補足3：`--login` はターミナルの入力を待たない

以前は Enter を待っていたが、CLI AI の実行環境や `!` 経由では標準入力が閉じており、
`input()` が即座に `EOFError` になって落ちる。**ブラウザの窓を閉じたら完了**とする。

### 変わらず確認できていること

| 項目 | 状態 |
|---|---|
| `#heatmapVisual` がスクロールコンテナであること | 実機で確認 |
| `scrollTop` の書き換えで**ページ画像と熱が同期して動く**こと | 実機で確認。クリック順位のバッジがボタンの上に正確に乗る |
| URLパラメータだけで期間・デバイス・種別・対象URLを再現できること | 実機で確認 |

`#heatmapVisual` のidが変わった場合に限り、
「スクロール可能でclientHeightが大きい要素」を探すフォールバックに切り替わる。
**idがある限り、この探索は使わない**（⑦の取り違えを防ぐため）。
それでも見つからない場合はエラーで止まる。

## 5. 既存ツールとの使い分け

| ツール | 方式 | 向いている場面 |
|---|---|---|
| `clarity_heatmap_capture.py` | ブラウザ自動化。`scrollTop` を直接制御 | 毎月同じ条件で撮り直す。複数の状態を機械的に並べる |
| `clarity_auto_capture_v2.py` | 画面キャプチャ。キーボードでスクロール | 自動化が通らない画面。ブラウザ拡張や別ツールの画面も撮れる |
| `concat_captures.py` | 画像の重なり検出で結合 | 撮影済みの連番画像を後から結合する |

`clarity_heatmap_capture.py` は結合位置を `scrollTop` から計算するため、
`concat_captures.py` の重なり検出は不要。手元にある連番画像を結合する場合は従来どおり使う。

## 6. 画像を所見にするときの注意

画像が揃っても、色の濃さだけで意図や不満を断定しない（`AGENTS.md`）。

- 熱の位置と画面要素の対応を、**要素名または画面領域の言葉**で記述する
- 期間・デバイス・サンプル数（ページビュー数）を必ず併記する
- 「押されている」ことと「押したかった」ことは別。仮説として分けて書く
- 数値で語れる部分は画像判読ではなく実数を使う → [CLARITY_METRICS.md](CLARITY_METRICS.md)
