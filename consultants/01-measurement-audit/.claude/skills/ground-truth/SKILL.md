# /ground-truth — 計測監査（レポートの独立検証／第三者評価シミュレーター）

> 日本語名は **「計測監査（けいそくかんさ）」**。通称「裏取り」。
> ユーザーに対して本スキルを指す際は、`GROUND TRUTH` ではなくこの呼称を使うこと。

あなたはこれから、**このレポートを外部の第三者評価機関として検証する**。
制作側の立場を降りること。自分（または過去のセッション）が作ったレポートであっても、
「初めて見る他社の成果物」として扱う。

## このスキルが解こうとしている問題

レポートの品質チェックには2つの層がある。

| 層 | 問うこと | 既存の `/final-check` 等 | 計測監査 |
|---|---|---|---|
| 第1層 | 数字は正しく転記されているか。体裁は崩れていないか | ○ | ○（前提として実施） |
| 第2層 | **その数字を出した計測器は、そもそも正常に動いているか** | × | **○（本スキルの中心）** |

実務で結論を壊すのは、ほぼ第2層である。
記載値と実測値が完全に一致していても、GA4側の設定が壊れていれば、
**「壊れた計測器の目盛りを、壊れていることに気づかないまま読んだ」**レポートができあがる。
数値監査だけでは、これを一度も検出できない。

本スキルの目的は、**納品前に自分でこの検査を通しておく**ことである。

## 大前提（評価者の心構え）

1. **制作側の集計を一切使わない。** 生データ（GA4/SCのエクスポート、管理画面、実サイト）に自分で当たる。
   レポートの表を読んで「そう書いてあるから」で確認済みにしない。
2. **指摘は、確定させる前に必ず反証を試みる。** 「別の説明が成り立たないか」を最低3つ検討し、
   それぞれが観測事実と矛盾することを確認してから確定させる（`references/04_対抗仮説カタログ.md`）。
   反証できなかった指摘は、確定ではなく「疑い」として書く。
3. **評価者自身の誤りを開示する。** 検証の過程で撤回・訂正した見解は、全件を報告書の最終章に載せる。
   これを載せない評価は信用されない。
4. **数値は1つも暗算しない。** 突合・比率・偶奇・分布はすべてスクリプトで計算する。
5. **提案を安易に否定しない。** 根拠が誤っていても、提案の方向自体は正しいことが多い。
   その場合の判定は「撤回」ではなく「根拠の差し替え」である。
6. **修正はしない。指摘のみ。** 報告書を出したあと、ユーザーの指示があった項目だけ直す。

## 手順

### Phase 0. 準備と範囲の確定

1. 引数のレポートパスを確認する。無ければカレント配下の最新 `.pptx` / `.pdf` を提示して確認する。
2. ラン用フォルダを作る：`_runs/<YYYYMMDD_HHmm>_groundtruth/`（以下 `$RUN`）。
3. 対象を明確にする。**ここを曖昧にしたまま進めない。**
   - 評価対象レポート（ファイル名・版）／対象サイト・ドメイン／対象期間／宛先
   - **対象範囲の外にあるドメイン**（別ドメインのEC・予約サイト・広告LP等）。
     ここを確認しないと、後で「最大の出口が対象範囲の外にあった」という見落としが起きる。
4. 生データの所在を確認する。足りないものは `references/05_必要データ一覧.md` を見て、
   **ユーザーに具体的に依頼する**（GASの実行を依頼できる場合は `gas/GA4_GroundTruth_監査データ取得.gs` を渡す）。
   データが揃わない項目は「未検証」として第7章に明記し、勝手に推測で埋めない。

### Phase 1. 機械抽出

```
python scripts/gt_extract.py <対象レポート> $RUN/extract
python scripts/gt_instrument_check.py <生データ...> --out $RUN/instrument
```

- `$RUN/extract/text.md` … レポート全文
- `$RUN/extract/numbers.json` / `numbers.md` … 数値台帳
- `$RUN/instrument/findings.md` … 計測健全性の検査結果（I-01〜I-10）

`gt_instrument_check.py` の出力は**指摘の下書きであって、指摘そのものではない**。
必ず Phase 3 の反証を通してから採用する。

### Phase 2. 転記精度の検証（数値突合）

1. `numbers.md` を読み、レポートに出てくる主要な数値をすべて洗い出す。
2. 生データから同じ数字を**自分で再集計**する（Pythonで計算。レポートの表を写さない）。
3. 突合定義JSONを作り、突合表を出す：

```
python scripts/gt_reconcile.py $RUN/reconcile.json --numbers $RUN/extract/numbers.json --out $RUN/突合表.md
```

4. 派生表現（「約N倍」「N%増」「合計」「うちN」「構成比」）を全部拾い、元の数字から再計算して照合する。
   セグメント別の値がある場合、全体値と加重平均・合計で整合するかを必ず検算する。

**ここで不一致が出なかったこと自体が、重要な所見である。** 報告書に明記する。

### Phase 3. 計測器の健全性検査（本スキルの中心）

`references/01_検査カタログ.md` の I-01〜I-10 を**全項目**実施する。
`gt_instrument_check.py` が自動で回すのは分布・比率の部分だけで、
次の項目は自分で確認する必要がある。

- **キーイベント（CV）の設定**：GA4管理画面のキーイベント一覧（画面キャプチャをユーザーに依頼）。
  page_view・first_visit・scroll・click が入っていないか。
- **0件のCVイベント**：名前がCVらしいのに0件のイベントが無いか。
  「成果が無い」のか「計測できていない」のかは、打ち手が正反対になるため必ず区別する。
- **実サイトの構造**：主要ページの CTA のリンク先を**実際に見に行く**。
  GA4だけで完結させない。外部ドメインへ出ていく導線は click イベントでしか観測できない。
- **ファネルの母集団**：ファネルの各段が同じ1ページの数字か。
  拡張計測機能の `form_start` / `form_submit` はフォームの種類を区別せず、
  サイト全体の合計しか返さない（『イベント』レポートにしか出ない）。
  ページ到達数の下にこれを置くと、割り算そのものが成立しない。

各検査で「所見なし」だった項目も、報告書に**所見なしとして記載する**。
何を見て何が無かったのかが分からない報告書は、検証されていないのと同じ。

### Phase 4. 反証（指摘を確定させる前に必ず通す）

検出した各所見について、`references/04_対抗仮説カタログ.md` を使い、
**最低3つの対抗仮説**を立てて順に潰す。潰せない仮説が残った所見は、
「確定した指摘」ではなく「未確定・要確認」として第7章に回す。

例（二重発火の場合に潰すべき仮説）：
1. 本当に全員が2回ずつ見ている → 利用規約ページや個別商品ページまで揃って2.00になるか？
2. アクティブユーザーの定義のせい → 分母が小さくなるだけで1.0が2.0になる説明にはなるか？
3. 計測タグが2セット入っている → それなら session_start も2倍になるはずだが、なっているか？
4. 表示回数が別のものを数えている → page_view のイベント数と表示回数の合計は一致しているか？

### Phase 5. 結論の再評価

補正後のデータで、**レポートの結論そのもの**が依然として成立するかを判定する。

- エグゼクティブサマリーの各文を1つずつ取り出し、「補正後も言えるか」を判定する。
- ボトルネック・勝ちページ・弱いページの認定が、補正後に**反転しないか**を確認する。
  （反転する例：外部ドメインへの流出を見落としていた場合、「CVに繋がらない弱いページ」が
  「最も強く次の行動を起こさせているページ」に変わる）
- 何が使えて何が使えないかの一覧を作る。ふつう、絶対値は使えなくなるが、
  **ページ間の相対的な大小関係・構成比・順位は生き残る**（全ページが等しく倍になるため）。
  ここを丁寧に切り分けると、レポートを全部書き直さずに済む。

### Phase 6. 改善提案の妥当性判定

レポートの提案を1件ずつ、補正後のデータで判定する。判定は3段階：

| 判定 | 意味 |
|---|---|
| 支持 | 補正後も成立する。記述の修正も不要か軽微 |
| 支持（根拠を差し替え） | 打ち手は妥当だが、根拠として挙げた数値・事実が誤っている |
| 再検討が必要 | 前提そのものが崩れており、事業側への確認が先に必要 |

**方向が正しい提案を、根拠の誤りだけを理由に否定しない。** これが評価の質を分ける。

### Phase 7. 発見の還元（指摘だけで終わらせない）

検証の過程で得られた「次版でそのまま使える材料」を D-01, D-02… として書く。
評価は減点作業ではない。生データを独立に触った者にしか作れない材料が必ず出る。

例：CV定義が未確定でも試算できる代替指標（CTA到達率 × 到達者の転換率）を見つける、
提案の裏づけになる数字を新たに計算する、測られていない導線の存在を指摘する、など。

### Phase 8. 報告書の作成

`references/03_報告書の構成.md` の構成に厳密に従って書く。
指摘1件ごとの書式は `references/02_指摘の書式と重要度.md` に従う。要点：

- 各指摘に **「ご自身で確認する方法」** を必ず付ける（相手が数十秒〜5分で再現できる手順）。
- 各指摘に **「修正の方向」** を必ず付ける。指摘して終わりにしない。
- **第8章に、評価側が撤回・訂正した項目を全件開示する。**
- **第7章に、未検証範囲と、追加で必要なデータを優先順位つきで書く。**

出力先：`$RUN/第三者評価報告書_<対象>_<日付>.md`

### Phase 9. ユーザーへの報告

チャットには次だけを出す（報告書本体はファイルで渡す）。

1. 総合判定（1〜3行）
2. 確定した指摘の一覧（番号・重要度・1行要約）
3. **いま追加で必要なデータ**（あれば。GASの実行を依頼する場合は関数名とシート名まで具体的に）
4. 報告書のパス

## やってはいけないこと

- 生データを見ずに、レポートの記述だけを読んで所見を書く。
- 反証を通さずに「重大」を付ける。特に I-01（二重発火）は影響範囲が広いため、必ず4仮説を潰す。
- 検出できなかった項目を報告書から省く（＝検査していないのと区別がつかなくなる）。
- 提案の方向性まで一緒に否定する。
- 自分の撤回・訂正を隠す。
- 「〜と思われる」で確定扱いする。推定は推定と書く
  （例：「確定できるのは『問い合わせフォームの送信ではない』ことまで。
  『メールマガジン登録である』は最有力という推定にとどまる」）。
