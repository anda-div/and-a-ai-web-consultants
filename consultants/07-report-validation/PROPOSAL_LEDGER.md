# 提案が枯渇しない仕組み／実装された提案を追いかける仕組み

毎月同じサイトを見て、同じ指標を見て、新しい改善提案を出す。
数か月続けると「もう出すことが無い」という状態になります。

そして出した提案は、実装されたのかどうかも分からないまま消えていきます。

どちらも発想力や熱意の問題ではありません。**性質の違う2つの問題**が混ざっているだけです。

| | 問題 | 性質 |
|---|---|---|
| **A** | 決まらない・うやむやになる | **組織の問題** |
| **B** | 効果が確認できない | **方法の問題** |

**この2つを混ぜると、実装されなかった提案のための立派な効果測定設計ができあがります。**
分けて扱います。

---

## A. 決まらない問題

### 現場で起きていること

支援会社が改善を提案しても、採用するかどうかはクライアント社内の会議で決まります。
いつ決まるかは不確定で、多くの場合うやむやになります。
「あの改善案はどうなりましたか」と聞くと「いろいろ忙しくてね」で流れます。

さらに、**改善にかかる社内工数と外注費に、誰も責任を取りたがりません。**
UI/UXの改善は効果が確認しにくいため、費用を出す判断に根拠を持たせにくいからです。

### 「自分で直せば無料」は前提にできない

ここが設計上いちばん重要な点です。

**テキスト1文字の修正でも外注する事業会社は珍しくありません。**
費用の問題ではなく、**責任の所在をはっきりさせるための判断**です。
自分で直して問題が起きるより、外部に依頼した記録を残しておきたい。
これは組織として合理的な行動で、否定しても変わりません。

したがって、

- ❌ 「コストゼロで直せます」＝**自分でやってください、と言っているのと同じ**
- ⭕ 「低コスト帯です」＝**外注しても金額が小さい**

前者は反発を招きます。**外注することを前提に設計してください。**

### 対処1 — 費用帯で分ける

`defaults/ledger_rules.json` の `cost_bands` で3段階に分けます。
**内製できるかどうかではなく、外注したときの金額感**で分けます。

| 帯 | 工数 | 通し方 |
|---|---|---|
| **低** | 文言のみ／設定のみ／ラベル追加／文言＋配置 | まとめて1回の発注にする |
| **中** | 軽微改修 | 見積が必要。低コスト帯で実績を作ってから出す |
| **高** | 中規模改修／中期 | 単発では通らない。次期リニューアルの要件に入れる |

```bash
python scripts/ledger.py --low-cost
```

### 対処2 — まとめて1回の発注にする

**1文字の修正でも、見積・発注・検収の手続きは1件ぶん発生します。**
金額ではなく**手続きの回数**が、実装されない理由になっている案件が少なくありません。

低コスト帯を個別に出すと、件数ぶん手続きが増えます。
まとめて1つの依頼にすれば、見積も決裁も検収も1回で済みます。

そのために、低コスト帯の提案には **`vendor_brief`（制作会社にそのまま渡せる指示）** を必ず書きます。

```json
"vendor_brief": "LP③の追従バーの文言「24時間以内に変身」を「24時間以内に返信」へ修正。他の箇所は変更しない。"
```

「他の箇所は変更しない」まで書くのが要点です。
**担当者が最も恐れているのは費用ではなく、頼んだ範囲を超えて壊されることです。**
指示が閉じていれば、その不安が減ります。

#### 発注依頼書を出す

```bash
python scripts/ledger.py --order-sheet --vendor 制作 --issued 2026-09-02
```

低コスト帯を1枚にまとめた、そのまま渡せる依頼書が出ます。

**発注先を必ず指定します。** 同じ費用帯でも、文言の修正・広告の配分変更・計測の実装は
渡す相手が違います。指定せずに実行すると、発注先の一覧を出して止まります。

依頼書の末尾で **反映日を尋ねている**のが要点です。
ここが返ってこないと、翌月の前後比較ができません。

```text
| 管理番号 | 反映日 |
|---|---|
| P-2026-06-006 | 　 |
```

なお、依頼書には**社内向けの背景（なぜ効くと考えているか）を載せません。**
それはレポートに書くことであって、作業の依頼書には要りません。
載せると、意図しない解釈や余計な配慮を招きます。

### 対処3 — 状態を「聞く」のではなく「書いて訂正してもらう」

「あれはどうなりましたか」は**一方向の催促**になります。
答えるほうは「まだです」としか言えず、気まずいだけの往復になります。
台帳をこの使い方にすると、**関係を悪くする道具**になります。

代わりに、こちらの理解を記入した一覧を出して、**違うところだけ訂正してもらいます。**

```bash
python scripts/ledger.py --status-sheet 2026-09
```

```text
| ID | 提案 | 工数 | こちらの理解 | 訂正 |
|---|---|---|---|---|
| P-2026-06-006 | LP③追従バーの文言修正 | 文言のみ | まだご返答をいただいていません |  |
```

**空欄を埋めるより、書かれた内容を直すほうが答えやすい。** これだけで回収率が変わります。

### 対処4 — 「保留」を日付のある状態にする

うやむやの正体は、**却下でも実施でもない第3の状態に名前が無いこと**です。
「検討中」「次のリニューアルで」と言われた提案は、誰も反対していないのに実行されません。

台帳では、保留にするとき次の2つを必須にしています。入れないとエラーになります。

- `blocked_by` — **何待ちか**（予算／制作会社の見積／次期リニューアル）
- `revisit_on` — **いつ再検討するか**

```bash
python scripts/ledger.py --set P-2026-06-005 --status 保留 \
  --blocked-by "次期リニューアルの要件確定" --revisit-on 2026-12
```

期日が来た保留は、月初ブリーフィングが自動で持ち出します。

```bash
python scripts/ledger.py --revisit-due 2026-12
```

**催促ではなく、期日が来たという事実として出します。** 誰も蒸し返していないのに、議題に戻ります。

## B. 効果が確認できない問題

### まず、正直に認めること

UI/UXの改善が売上に寄与したかを証明することは**できません。**

- 改善を進める間に、広告配信のロジックが変わっている
- 競合の戦術が変わっている
- 誰も悪くないのに売れなくなる商材がある
- 半年前に正しかったUIが、いま古く見えることがある

これらを全部織り込むには、全地球気象予測より複雑なモデルが要ります。
**「投資対効果を証明します」と言ってはいけません。**

### ただし、測れるものはある

業界がここで犯している間違いは、**測ろうとしているものが違う**ことです。

> 「送信ボタンのコントラストを上げたら、**売上**が上がったか」— 測れません。
> 「送信ボタンのコントラストを上げたら、**フォームに到達した人のうち入力を始めた人の割合**が変わったか」— **測れます。**

なぜ測れるか。**分子と分母が、同じページの同じ段階にあるからです。**

広告のロジックが変わっても、競合が動いても、季節が変わっても、
**分子と分母の両方に等しくかかります。** だから比率は残ります。

セッション数は環境で動きます。しかし「到達→開始の率」は動きにくい。

> **局所の比率は、外部環境の変化に対して頑健です。**

### だから、提案を出す時点で比率を決める

`defaults/ledger_rules.json` の `metric_rules` に基準があります。

| | 例 |
|---|---|
| **良い** | 到達→開始の率／開始→送信の率／商品閲覧→カート追加の率／FV到達→次セクション到達の率 |
| **避ける** | セッション数／問い合わせ件数／売上／検索順位（他社の動きで動く） |

比率にできない提案もあります。計測そのものを始める提案などです。
その場合は絶対数で構いませんが、**「環境で動く指標である」と明記し、単独で成否を判断しません。**

### 証明できないことと、判断できないことは違う

ここが、クライアントへの説明で最も効くところです。

50万円が回収できたかは**証明できません。**
しかし、**次にどちらへ投資するか**を決めるためなら、局所の比率で十分です。

- A案（CTA配置）は局所比率が動いた
- B案（価格表示）は動かなかった
- → 次はA型の施策に寄せる

これは証明ではありません。**しかし判断としては合理的です。**

業界はここを混同しているため、「効果が測れないなら測るのをやめよう」になっています。
正しくは「**証明はできないが、判断はできる**」です。

### 効果検証の書き方

`metric_rules` と `verification_writing` に型があります。

**書くこと**

- 比較した期間と日数（**同じ日数で切る**）
- 指標が比率か絶対数か
- 同時期に起きた他の変化（広告の出稿変更、競合の動き、季節要因）

**書いてはいけないこと**

- 「この施策により売上が◯◯円増加した」
- 「投資対効果は◯◯%だった」
- 「効果が実証された」

**代わりに書くこと**

- 「狙った指標は動いた。ただし同時期に◯◯も変わっているため、この施策だけの効果とは言い切れない」
- 「動かなかった。次は◯◯を確かめる」
- 「次にどこへ投資するかの判断材料として、A型の施策を優先する」

**言い切らないことが信頼になります。**

### 失敗も資産になる

いま多くの現場で起きているのは「効果が分からない」より一段手前の問題です。
**そもそも実装されたかどうかが分からない。** だから効かなかった施策からも学べません。

台帳があると、効かなかったことも記録に残ります。3年続ければ、

> 「このクライアントでは、CTA系の施策は局所比率が動いたが、価格表示系は動かなかった」

という**そのクライアントに固有の知見**が溜まります。
ツールは真似できますが、**3年分の記録は真似できません。**

## C. 提案が枯渇しない仕組み

「もう出すことが無い」の原因は3つです。

| 起きること | 原因 | 対処 |
|---|---|---|
| 前に同じ案を出した気がして出せない | 憶えていられない | **提案台帳** |
| 毎月同じ結論に着地する | 見る角度が固定されている | **切り口カタログのローテーション** |
| 前の提案が次の提案を生まない | 結果を確かめる前に次の月が来る | **実装日の記録と前後比較** |

### 提案台帳 `scripts/ledger.py`

```bash
python scripts/ledger.py --pending                    # まだ実装されていないもの
python scripts/ledger.py --low-cost                   # まとめて発注できる候補
python scripts/ledger.py --verify-due 2026-07         # その月に検証すべきもの
python scripts/ledger.py --revisit-due 2026-12        # 再検討の期日が来た保留
python scripts/ledger.py --status-sheet 2026-09       # 打ち合わせ用の確認シート
python scripts/ledger.py --angle price_transparency   # 切り口で照会
python scripts/ledger.py --set P-2026-06-001 --status 実装済み --date 2026-07-15
```

#### 照会は「切り口」で行う

文字列の似ている・似ていないだけでは足りません。

> 「料金を分かりやすく表示する」
> 「料金・最低保証を事前提示し、依頼フローを図解する」

同じことを言っているのに、共通する文字がほとんどありません。
そこで**切り口（`angle`）を最も強い手がかり**にしています。
提案を出すときは自分が使った切り口が分かっているはずなので、必ず `--angle` を渡します。

#### 却下も残す

消しません。理由ごと残します。理由が2つの働きをします。

- 同じ案を出し直さない
- **状況が変われば再提示できる**（「今期は予算が無い」で却下された案は、翌期に出し直せる）

### 切り口カタログ `defaults/angles_catalog.json`

分析の切り口を32本。集客／回遊／転換／検索／競合／時間／会員／商品／記述／計測。

各項目が持つのは名前ではなく**問い**です。`question` が具体的でないと所見がぼやけます。

毎月、**直近3か月で使っていない切り口から選びます。** 使ったものは履歴に記録します。

競合比較で既に使っている考え方と同じです。
中核数社を固定し残りを毎月入れ替えるから、毎月新しい発見が出る。
**新しさはひらめきではなく、ローテーションが生みます。**

### 月初ブリーフィング `scripts/build_briefing.py`

```bash
python scripts/build_briefing.py 2026-07
```

| 節 | 誰が用意するか |
|---|---|
| 台帳の状況／低コスト帯／期日が来た保留／検証すべき提案／使える切り口／主要指標 | **機械** |
| 提案候補10本 | **AI**（依頼文が同梱される） |
| どれを載せるか、言い切り方、相手への配慮 | **人** |

- **機械**は事実を揃える。憶えること・数えること・照合することは、人がやる必要がない
- **AI**は候補を出す。10本のうち何本かは使えないが、それでよい
- **人**は選んで磨く。効果の言い切り方、相手への配慮、打ち合わせとの整合は人にしか分からない

**「考え出す」から「選んで磨く」に変わります。** 丸投げではありません。
白紙の前で悩む時間だけが無くなります。

## D. 毎月の流れ

```text
データを置く
  ↓
python scripts/build_briefing.py <対象月>       ← 機械が事実を揃える
  ↓
ブリーフィングを CLI AI に渡す                   ← AIが候補を10本出す
  ↓
候補から3〜5本を選び、レポートに書く              ← 人が選んで磨く
  ↓
選んだ提案を台帳へ登録／使った切り口を履歴へ        ← 次の月の資産になる
  ↓
打ち合わせで --status-sheet を出す                ← 状態を書いて訂正してもらう
  ↓
低コスト帯はまとめて1回の発注にする                ← 手続きの回数を減らす
  ↓
実装されたら実装日を記録 → 翌月に前後比較
```

## E. 何を約束し、何を約束しないか

| 言えること | 言えないこと |
|---|---|
| 提案が消えなくなる（**仮説ではなく確実**） | 投資対効果を証明する |
| 実装したものは環境変化に強い指標で前後比較できる | 売上が上がる |
| 次にどこへ投資すべきかの判断材料が積み上がる | 効果を保証する |

不確定要因そのものは減りません。広告のロジックも競合も、変わり続けます。

減るのは、**不確定要因のうち自分たちの側にあった分**です。

- 提案を忘れる
- 実装されたか分からない
- 何を測るか決めていない
- 去年と同じことを言っている

これらは外部環境ではなく、**自分たちの側の問題**です。そして完全に消せます。

外の霧は晴らせませんが、**足元の霧は晴らせます。**

## 効果をどう示すか

「楽になった」を感覚で終わらせないために、導入前に一度だけ測っておきます。

| 測るもの | 測り方 |
|---|---|
| 提案の初稿ができるまでの時間 | データを置いてから提案が固まるまでの実時間 |
| 月あたりの提案候補数 | 検討の俎上に載った案の数（採用したものだけではない） |
| 過去提案との重複確認にかけた時間 | 過去のレポートを読み返した時間 |
| 提案の実施率 | 出した提案のうち、実装済み・却下が確定した割合 |

最後の1つが、Aの問題に対する成果指標です。
**「実施された割合」ではなく「状態が確定した割合」**であることに注意してください。
却下も、うやむやよりずっと良い結果です。

## 置き場所

| 公開側（このリポジトリ） | 利用者側 |
|---|---|
| `scripts/ledger.py` 台帳の読み書き | `_ledger/proposals.json` 提案の中身 |
| `scripts/build_briefing.py` ブリーフィング生成 | `_ledger/angles_history.json` 切り口の履歴 |
| `defaults/angles_catalog.json` 切り口カタログ | `_runs/briefing_<月>.md` 出力 |
| `defaults/ledger_rules.json` 費用帯・指標・保留のルール | |

台帳と履歴は**設定ではなく、積み上がっていく記録**です。
そのため `_config/` ではなく `_ledger/` に置きます。
`_config/` は人が書く設定、`_ledger/` はスクリプトが書き足す記録、という分け方です。

カタログとルールは公開側にあるので、**改善すれば次の更新で全利用者へ届きます。**
