# 提案が枯渇しない仕組み

毎月同じサイトを見て、同じ指標を見て、新しい改善提案を出す。
数か月続けると「もう出すことが無い」という状態になります。

これは発想力の問題ではありません。次の3つが揃っていないだけです。

| 起きること | 本当の原因 |
|---|---|
| 前に同じ案を出した気がして、出せない | **出した提案を憶えていられない** |
| 毎月同じ結論に着地する | **見る角度が固定されている** |
| 前の提案が次の提案を生まない | **実装した結果を確かめる前に次の月が来る** |

3つとも、道具で埋められます。

---

## 1. 提案台帳 — 憶えていなくてよくする

`scripts/ledger.py` が読み書きします。中身は利用者側（`_ledger/proposals.json`）に置きます。

### 記録する項目

| 項目 | 内容 |
|---|---|
| `id` | `P-2026-06-001` の形。出した月が入るので、いつの提案か一目で分かる |
| `title` `target` | 提案の内容と、対象のURL |
| `angle` | どの切り口から出たか（後述のカタログのキー） |
| `evidence` | 根拠。どのデータの何の数値か |
| `effort` | 文言のみ／設定のみ／軽微改修／中規模改修／中期 |
| `metric` `baseline` | 効く指標と、提案時点の値。**ここが翌月の検証の起点になる** |
| `status` | 提案中／実装待ち／実装済み／検証済み／却下／保留 |
| `status_note` | とくに**却下の理由**。これが無いと同じ案を出し直す |
| `implemented_on` | 実装日。入っていれば前後比較ができる |
| `verification` | 検証の結果 |

### 使い方

```bash
python scripts/ledger.py --pending                    # まだ実装されていないもの
python scripts/ledger.py --verify-due 2026-07         # その月に検証すべきもの
python scripts/ledger.py --angle price_transparency   # 切り口で照会する
python scripts/ledger.py --similar "追従CTAを置く" --angle cta_placement
python scripts/ledger.py --set P-2026-06-001 --status 実装済み --date 2026-07-15
```

### 照会は「切り口」で行う

文字列の似ている・似ていないだけでは足りません。

> 「料金を分かりやすく表示する」
> 「料金・最低保証を事前提示し、依頼フローを図解する」

同じことを言っているのに、共通する文字はほとんどありません。
そこで**切り口（`angle`）を最も強い手がかり**にしています。
提案を出すときは自分が使った切り口が分かっているはずなので、必ず `--angle` を渡します。

### 却下された提案も残す

消しません。理由ごと残します。理由が2つの働きをするためです。

- 同じ案を出し直さない
- **状況が変われば再提示できる**（「予算が無い」で却下された案は、翌期に出し直せる）

## 2. 切り口カタログ — 見る角度を固定させない

`defaults/angles_catalog.json` に、分析の切り口を並べてあります。
集客／回遊／転換／検索／競合／時間／会員／商品／記述／計測 の分類です。

各項目が持つのは、名前ではなく**問い**です。

```json
{
  "key": "form_funnel",
  "name": "フォームの段階別離脱",
  "question": "到達・開始・送信のどこで落ちているか",
  "needs": ["ga4.form_events"],
  "typical": "入力を始める前に落ちている＝書ける状態になっていない",
  "leads_to": "項目の見直し、書き方の例示、送信導線の是正"
}
```

`question` が具体的でないと所見がぼやけます。カタログを増やすときも、まず問いを書いてください。

### ローテーション

毎月、**直近 `cooldown_months`（既定3か月）で使っていない切り口から選びます。**
使った切り口は `_ledger/angles_history.json` に記録します。

これは競合比較で既に使っている考え方と同じです。
中核数社を固定し、残りを毎月入れ替えるから、毎月新しい発見が出ます。
**新しさはひらめきではなく、ローテーションが生みます。**

`typical`（出やすい所見）はそのまま書き写さないでください。
今月の数字で確かめて、違っていたらそれ自体が発見です。

## 3. 月初ブリーフィング — 白紙の前で悩ませない

`scripts/build_briefing.py` が、データを置いた直後に1枚のMarkdownを作ります。

```bash
python scripts/build_briefing.py 2026-07
```

| 節 | 誰が用意するか |
|---|---|
| 1. 台帳の状況（未実装・却下） | 機械 |
| 2. 今月、効果を検証すべき提案 | 機械 |
| 3. 今月の切り口候補（未使用のもの） | 機械 |
| 4. 今月の主要指標 | 機械 |
| 5. 提案候補 **10本** | **AI**（依頼文が同梱されている） |
| 6. 人が決めること | **人** |

役割の分け方が要点です。

- **機械**は事実を揃える。憶えること・数えること・照合することは、人がやる必要がない
- **AI**は候補を出す。10本のうち何本かは使えないが、それでよい
- **人**は選んで磨く。効果の言い切り方、相手への配慮、打ち合わせとの整合は人にしか分からない

**「考え出す」から「選んで磨く」に変わります。** 丸投げではありません。
白紙の前で悩む時間だけが無くなります。

## 4. 効果検証が次の提案を生む

実装された提案は、翌月に同じ条件で前後比較します（`scripts/compare_periods.py`）。

- **効いた** → 同じ型を他のページへ展開する、が次の提案になる
- **効かなかった** → なぜか、が次の問いになる

どちらでも次が生まれます。ここが回り始めると枯渇しません。

そのために必要なのは**実装日の記録だけ**です。
「いつ実装したか」が分からないと、前後比較のしようがありません。
月次の打ち合わせで実装状況を聞き、その場で台帳へ入れてください。

---

## 5. 毎月の流れ

```text
データを置く
  ↓
python scripts/build_briefing.py <対象月>     ← 機械が事実を揃える
  ↓
ブリーフィングを Claude Code に渡す            ← AIが候補を10本出す
  ↓
候補から3〜5本を選び、レポートに書く            ← 人が選んで磨く
  ↓
選んだ提案を台帳へ登録／使った切り口を履歴へ      ← 次の月の資産になる
  ↓
翌月、実装されたものを検証する
```

---

## 6. 効果をどう示すか

「楽になった」を感覚で終わらせないために、導入前に一度だけ測っておきます。

| 測るもの | 測り方 |
|---|---|
| 提案の初稿ができるまでの時間 | データを置いてから、提案が固まるまでの実時間 |
| 月あたりの提案候補数 | 検討の俎上に載った案の数（採用したものだけではない） |
| 過去提案との重複確認にかけた時間 | 過去のレポートを読み返した時間 |

3か月後に同じものを測れば、**実測の削減率**として言えます。
数字を置かずに「大幅に楽になりました」と言うと、次に何を改善すべきかも分からなくなります。

## 置き場所

| 公開側（このリポジトリ） | 利用者側 |
|---|---|
| `scripts/ledger.py` 台帳の読み書き | `_ledger/proposals.json` 提案の中身 |
| `scripts/build_briefing.py` ブリーフィング生成 | `_ledger/angles_history.json` 切り口の履歴 |
| `defaults/angles_catalog.json` 切り口カタログ | `_runs/briefing_<月>.md` 出力 |

台帳と履歴は**設定ではなく、積み上がっていく記録**です。
そのため `_config/` ではなく `_ledger/` に置きます。
`_config/` は人が書く設定、`_ledger/` はスクリプトが書き足す記録、という分け方です。

カタログは公開側にあるので、切り口を増やせば**次の更新で全利用者へ届きます。**
