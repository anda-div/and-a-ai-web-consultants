# /final-check — 納品前最終チェック

あなたはこれから、納品直前のPPTXレポートの**独立チェッカー**として動く。

## 大前提（チェッカーの心構え）

- **「このレポートには必ず誤りが含まれている」前提で探す。** 見つからないのは探し方が足りない。作成者（過去のセッション）の判断を信用しない。
- **数値は1つも暗算しない。** 倍率・合計・構成比・加重平均の検算はすべてPythonで計算する。
- **修正は行わない。指摘のみ。** 報告書提出後、ユーザーから指示があった項目だけを修正する。
- このスキルは**レポートを作成したセッションとは別の新規セッションで実行すること**（同一セッションで起動された場合はその旨を警告した上で続行してよい）。

## 手順

### Phase 0. 準備

1. 引数のPPTXパスを確認。引数がなければ、カレントフォルダ配下で最新の `.pptx` を提示してユーザーに確認する。
2. プロジェクト直下の `設定_固有名詞.txt` を読む（G-1・G-4のチェックに使う）。
3. ラン用フォルダを作成: `_runs/<YYYYMMDD_HHmm>_<ファイル名の主要部>/`（以下 `$RUN`）。
4. 案件フォルダに修正依頼・追記依頼・与件などのファイル（例: `修正依頼-*.txt` `与件-*.txt`）があれば読み込む（S-2の突合に使う）。

### Phase 1. 機械抽出

```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/render_slides.ps1 -PptxPath <対象.pptx> -OutDir $RUN/slides
python scripts/extract_pptx.py <対象.pptx> $RUN/extract
```

（PowerShell 7 がある環境では `powershell` の代わりに `pwsh` でもよい）

- `$RUN/slides/slideNNN.png` … 全スライドのレンダリング画像
- `$RUN/extract/text.md` … 全テキスト（ノート含む）
- `$RUN/extract/numbers.json` … 数値台帳

PowerPointが起動できない・枚数が合わない場合はそこで停止してユーザーに報告する。

### Phase 1.5. 機械による「ありえない値」の検査（Phase 2 の前に必ず）

```
python scripts/check_values.py <対象.pptx> --period <YYYY-MM> --prev <前月の納品.pptx> | tee $RUN/values.txt
python scripts/check_layout.py <対象.pptx> | tee $RUN/layout.txt
```

`check_values.py` は、人が読み落とす類の**ありえない値**を機械で拾う。
実際に起きた事故から作られている。

| 実際に起きたこと | 拾う項目 |
|---|---|
| 3ブランドの要点ページがそろって「収益 ¥0」（描く側が古い参照先を読んでいた） | そろって0 / 前月から0へ |
| 「集計期間: 2026/08/01〜07/31」が4ページに残った（前月の表記の月だけ書き換えた残骸） | 期間の逆転 / 期間のずれ |
| 別チャネルの収益が1円まで同額 | 同額の重複 |
| 前月と1件も違わない導線の件数 | 前月と同一 |

**「要対応」が1件でもあれば、Phase 2 に進む前にユーザーへ報告する。**
「確認」は Phase 4 の目視で該当ページを開いて判断する。表の中の ¥0 は
規模の小さい区分で正当に起きるので、「確認」にとどめてある。

前月の納品ファイルが無い（初回）ときは `--prev` を省く。

### Phase 2. 数値トレーサビリティ検算（最重要）

`numbers.json` と `text.md` を読み、Pythonスクリプトを書いて以下を全数検証する:

1. **表記整合**：同じ指標を指す数値が複数スライドに登場する場合、値・丸め・桁数が完全一致するか（例: CVR 2.70% ↔ 2.68% のようなゆれ）。指標の同一性判定は文脈（context）から自分で判断する。
2. **導出整合**：「約N倍」「N%増」「N%減」「合計」「うちN」等の派生表現をすべて列挙し、元数値から再計算して一致確認（丸めは四捨五入で±最終桁1まで許容）。セグメント別数値（新規/既存・チャネル別・デバイス別）がある場合、全体値と加重平均・合計で整合するかを必ず検算する。構成比の合計が100%（±0.2pt）になるか。
3. **定義整合**：同名指標（CVR・CV・セッション等）の定義・分母・集計期間が全ページで同一と読み取れるか。異なる基準が混在する場合、注記で区別されているか。データ出所の台帳ファイル（`数値台帳*.json` 等）が案件フォルダにあれば突合する。

### Phase 3. 回帰チェックリスト

`CHECKLIST.md`（このスキルと同じプロジェクト直下）の**全項目**を実行する。

- 「機械」項目 → text.md へのgrep・スクリプトで全数チェック。G-1（他社名残存）は `設定_固有名詞.txt` の「登場してはいけない固有名詞」を全文検索し、さらに「登場してよい固有名詞」に載っていない社名・商品名・URLらしき固有名詞をすべて疑って列挙する
- 「検算」項目 → Phase 2の結果を割り当てる
- 「目視」項目 → Phase 4に組み込む

報告書には全項目のID別結果（検出あり／問題なし確認）を記載する。

### Phase 4. 全スライド目視（3視点）

`$RUN/slides/` の全PNGを**1枚残らず**Readで読む（1メッセージに複数Readで並行読み込み、5〜8枚ずつ）。各スライドを3つの視点で評価する:

- **① 数値検算係**：画像内の数値（グラフ軸・表・バッジ）とテキスト抽出の数値の一致。グラフの見た目（棒の高さ・円の割合）と数値ラベルの整合。凡例と実表示の一致。
- **② 日本語体裁係**：1文字行・行頭禁則（。、）」ー）・語中分断・句点孤立。フォント/サイズ/色の不統一。要素のはみ出し・重なり・切れ。キャプチャの文字切れ・細長すぎ・写り込み。
- **③ 初見読者係**：予備知識ゼロの読者として、このスライド単体で意味が通るか。未定義の記号・略語はないか。矛盾に見える数値の並び（内数関係の不明確さ）はないか。

スライドが30枚を超える場合は、Agentツールで**視点別サブエージェント3体**（各視点につき1体、全スライドを担当）を並行起動して分担してよい。その場合、各エージェントには該当視点の説明・PNGフォルダのパス・「所見をスライド番号付きで列挙して返す」ことを指示する。

### Phase 5. 報告書の出力

`$RUN/最終チェック報告.md` に以下の固定フォーマットで保存する:

```markdown
# 納品前 最終チェック報告書
- 対象ファイル / 全N枚 / チェック日 / チェック方法
- 本チェックではファイルの修正は行っていません。指摘のみです。

## 総評（納品可否の所見を一文で明言する）
| 区分 | 件数 | の表

## A. 重大（誤データ・定義不整合・指示適合漏れ — 対応推奨）
## B. 表現・数値の要確認
## C. 体裁（改行・禁則・1文字行）
## D. レイアウト・見栄えの改善余地（任意）
## 回帰チェックリスト実行結果（CHECKLIST.md全項目のID別: 検出あり/問題なし）
## 問題なしを確認した項目
## 対応優先度の提案
```

各指摘には必ず**スライド番号と具体的な位置・現状の文言・修正案**を書く。

### Phase 6. 人間チェックプロトコルの提示

最後にユーザーへのメッセージとして以下を提示する:

1. 報告書の要点（A・Bの件数と最重要指摘）
2. **抜き取り精読の対象スライド番号**：等間隔5枚（1枚目と最終枚を含む）＋数値密度上位3枚（numbers.jsonの件数順）
3. `人間チェックプロトコル.md` に沿って25分のチェックを行うよう案内

### Phase 7. 事後（チェックリストを育てる）

今回のチェックで**既存のCHECKLIST.mdに該当しない新種の問題**を見つけた場合、CHECKLIST.mdへの追加行を提案する（勝手に追加せず、報告書の末尾に「チェックリスト追加提案」として記載）。
