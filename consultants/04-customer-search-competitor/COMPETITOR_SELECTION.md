# 競合の選び方と、レポートへの載せ方

競合比較は、レポートの中で最も枚数を食う章になりやすく、生成コストと所要時間を
最も左右する部分です。一方で、改善提案の質はここで決まります。
この文書は、その両立のための判断基準をまとめたものです。

企業名や実際の選定結果は、この文書ではなく利用者側の設定ファイルに置いてください。

---

## 1. なぜ社数が要るのか

改善提案の論拠は、多くの場合この形を取ります。

> この打ち手は、**ほぼ全社が持っているのに自社が持っていない基本装備**です。

この言い方は、社数が確保されて初めて成立します。1社しか見ていなければ
「その1社がそうしている」としか言えず、提案の重みが変わります。

したがって **競合は最低3社**とします。3社を下回ると、改善提案は
自社データ（アクセス解析・ヒートマップ・ヒューリスティック分析）だけを根拠にすることになり、
発想の幅が落ちます。

## 2. なぜ上限が要るのか

社数を増やせば良いレポートになる、という保証はありません。
一方でコストと時間は増え続けます。上限を **12社**とします。

上限を設ける理由はもう一つあります。利用者が意図せず極端な数
（30社など）を指定した場合に、生成が破綻するのを防ぐためです。

## 3. 枚数を削るときは、社数ではなく「1社あたり」を削る

ここが最も重要な判断です。

| 案 | 社数 | 1社あたり | 合計枚数 | 「ほぼ全社が」と言えるか |
|---|---|---|---|---|
| A | 12社 | 1枚 | 12枚 | **言える** |
| B | 4社 | 3枚 | 12枚 | 言いにくい |

**同じ枚数なら、社数を保つほうが提案の質は高くなります。**
枚数の圧縮が必要なときは、まず1社あたりの枚数を減らしてください。

推奨は **1社1枚**です。1社に3枚使うのは、その競合が自社と極めて近く、
細部まで見る価値がある場合に限ります。

## 4. カテゴリーは各3社以上

「カテゴリー横断の共通強み」は、各カテゴリーに複数社あって初めて言えます。
1カテゴリー1社では、それがカテゴリーの特徴なのか、その1社の個性なのかを区別できません。

カテゴリーは、対象事業の構造に合わせて決めてください。
複数の事業ラインや顧客像を持つサイトでは、**カテゴリーを顧客像に対応させる**と、
どの章の指摘がどの顧客に効くのかを追えるようになります。

推奨は **3カテゴリー×3社＝9社**です。

## 5. 選び方は3つ。生成開始時に利用者へ尋ねる

どれが適切かは事業によって変わり、AIが決めるには選択肢が多すぎます。
レポート生成の開始時に、次の3つから選んでもらってください。

| 方式 | 内容 | 向いている場合 |
|---|---|---|
| 入れ替え | 毎月、その月の改善テーマに合わせて選び直す | 毎月新しい切り口を求められる |
| 固定 | 前月と同じ競合を継続する | 競合が明確に固定されている業界 |
| **固定コア＋入れ替え枠**（推奨） | 2〜3社を固定し、残りを毎月入れ替える | ほとんどの場合 |

固定コアがあると**推移の比較**ができ、入れ替え枠があると**新鮮な切り口**が得られます。

### AIが選定する場合の基準

**その競合から良い改善提案を引き出せそうか**、の一点で選びます。
アクセス数の多さや知名度の高さで選ぶのではありません。
自社データだけでは出てこない発想を補える相手を選んでください。

## 6. 同じ競合を再び取り上げる月

同じ競合でも、切り口が変われば見えるものは変わります。
「今月は商品の見せ方」「今月は購入後のサポート体制」と観点を変えれば、
同じサイトから別の学びが得られます。

ただし放置すると、前月の焼き直しになります。これを防ぐため、
**競合 × 月 × 切り口 × 抽出した所見**を履歴として記録してください。

再登場する月は、**前回の切り口を提示したうえで、今月は何を変えて見るかを明記**します。
（`docs/WORKFLOW.md` の「毎月の新規性」も参照）

## 7. キャプチャは差分方式で取る

競合サイトは毎月は変わりません。毎月全点を取り直すのは、
ほぼ同じ画像を作り直す作業になります。

1. **初回は全点取得**する。
2. 翌月以降は**ファーストビューだけ取得してハッシュを比較**する。
3. **変化があった競合だけ全点を取り直す**。変化がなければ前月の画像を再利用する。
4. 再利用した場合も、**キャプチャの取得日をレポートに必ず明記**する。
5. 差分が出なくても、一定期間（既定6か月）ごとに一度は全点を取り直す。

これで生成時間とAI使用料が下がり、品質は落ちません。

## 8. 上限は社数ではなく点数で持つ

コストは社数だけでは決まりません。

```
コスト ≒ 社数 × 1社あたり枚数 × デバイス数
```

12社×1枚なら12点ですが、12社×3枚×2デバイスなら72点です。
社数上限とは別に **キャプチャ点数の上限**（既定40点）を持ち、
超えそうな場合は生成前に警告してください。

## 9. 指定された競合が不適切なとき

利用者が指定した競合が、業態が離れすぎていて改善提案を引き出しにくいことがあります。

このとき、**黙って質の低いページを作らないでください**。
なぜ引き出しにくいのかを説明し、代替案を添えて、利用者に選んでもらいます。
指定を覆すのではなく、判断材料を出すという姿勢です。

## 10. 章の構成（レポートに載せるとき）

| # | ページ | 内容 |
|---|---|---|
| 1 | 先に結論 | 競合から最初に取り組む打ち手の一覧。工数の小さい順 |
| 2 | 競合一覧 | カテゴリ／サイト／代表的な所見／自社に取り込む候補 |
| 3 | 各社 | **1社1枚**。キャプチャ＋自社との差異＋自社への示唆 |
| 4 | 横断共通 | カテゴリーを横断する“効く型”と、最優先で参考にすべき施策 |

- 示唆は必ず**具体的な打ち手に翻訳**します。「良い」で止めない。
- 競合を貶さず、**学ぶべき点**を抽出する姿勢を保ちます。
- キャプチャは、解説で言及した要素が**実際に写っている**ものを使います。
  写っていない場合は、その要素が表示された状態で取り直してください。

## 設定例

レポート生成側の設定ファイルに、次の形で持たせます。
サンプルは [JOB 07 の config.example](../07-report-validation/config.example/) にあります。

```json
"competitor": {
  "selection_mode": "core_plus_rotating",
  "count": { "min": 3, "max": 12, "recommended": 9 },
  "pages_per_competitor": 1,
  "categories": { "list": ["（カテゴリA）", "（カテゴリB）", "（カテゴリC）"],
                  "per_category_min": 3 },
  "core": { "companies": ["（毎月固定の競合）"] },
  "capture_policy": { "mode": "diff", "full_recapture_months": 6 },
  "max_captures": 40,
  "history_file": "_config/competitor_history.json"
}
```
